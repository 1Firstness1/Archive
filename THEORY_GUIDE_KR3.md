## 1. Базовая теория ООП, систем типов и паттернов

### 1.1. Виды полиморфизма в ООП (классификация Карделли-Вегнера)
В теории языков программирования полиморфизм означает способность сущности (метода, оператора, класса) обрабатывать данные различных типов единым образом. Согласно фундаментальной классификации Луки Карделли и Питера Вегнера (1985 г.), выделяют **четыре вида полиморфизма**:

```
                       Виды полиморфизма
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
Универсальный (Universal)             Специальный (Ad-hoc)
    │                                     │
    ├─ Параметрический (Generics)         ├─ Перегрузка (Overloading)
    └─ Включения (Subtyping / Наследование) └─ Приведение (Coercion)
```

1. **Параметрический полиморфизм (Parametric Polymorphism / Дженерики):**
   * Позволяет описывать обобщённые алгоритмы и контейнеры безотносительно к конкретным типам. Тип подставляется как параметр во время компиляции: `JpaRepository<DocumentRequest, Long>`, `Specification<DocumentRequest>`, `ResponseEntity<T>`, `List<UUID>`.
   * **Назначение:** Обеспечение **строгой статической типобезопасности во время компиляции (Compile-Time Type Safety)**. Исключает ручное приведение типов `(DocumentRequest) obj` и предотвращает `ClassCastException`.
   * **Стирание типов (Type Erasure):** В байт-коде JVM информация о параметризованном типе `T` стирается до верхней границы (`Object` или указанного интерфейса), что гарантирует 100% обратную совместимость с ранними версиями Java.
2. **Полиморфизм включения (Subtyping / Inclusion Polymorphism / Наследование):**
   * Свойство, позволяющее ссылке на супертип указывать на экземпляр любого подтипа: `AuthenticationEntryPoint`, `PasswordEncoder`, `JpaSpecificationExecutor`.
   * Реализуется через динамическую диспетчеризацию вызовов (Virtual Method Table / VMT) во время выполнения (Runtime).
3. **Перегрузка (Overloading / Ad-hoc полиморфизм):**
   * Объявление методов с одним именем, но различными сигнатурами внутри одного класса. Резолвинг вызова происходит **статически на этапе компиляции**: конструкторы `Account(...)`, перегруженные методы `api.exportCsv(...)`.
4. **Полиморфизм приведения типов (Coercion):**
   * Неявное или явное семантическое преобразование типов: автоматический автобоксинг `int` в `Integer`, приведение чисел при делении.

### 1.2. Парадигма MVC и многослойная архитектура (Layered Architecture)
В проекте реализована классическая серверная **многослойная архитектура (N-Tier Architecture)** с четким разделением ответственности (SoC — Separation of Concerns):

```
┌────────────────────────────────────────────────────────────────────────┐
│                   Клиентский слой: React 18 SPA (Vite)                 │
│         Компоненты: RequestsView, DictionaryView, AdminView...          │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │ HTTP / JSON (REST API)
┌───────────────────────────────────▼────────────────────────────────────┐
│                    Web Layer: Spring Security Filters                  │
│       CorrelationIdFilter -> JwtAuthenticationFilter -> SecurityConfig │
├────────────────────────────────────────────────────────────────────────┤
│                    Controller Layer (REST Controllers)                 │
│   DocumentRequestController, AuthController, AnalyticsController...   │
│   Валидация (@Valid DTO), сопоставление маршрутов, HTTP-статусы         │
├────────────────────────────────────────────────────────────────────────┤
│                    Service Layer (Бизнес-логика)                       │
│   DocumentRequestService, AuthService, CsvService, BulkService...     │
│   Транзакции (@Transactional), права доступа, расчет метрик            │
├────────────────────────────────────────────────────────────────────────┤
│                    Persistence Layer (Spring Data JPA)                 │
│   DocumentRequestRepository, Specification, AccountRepository...       │
├────────────────────────────────────────────────────────────────────────┤
│                    Database Layer: PostgreSQL 15                       │
│   Таблицы, индексы, Flyway-миграции, внешние ключи, CHECK-ограничения  │
└────────────────────────────────────────────────────────────────────────┘
```

Каждый слой зависит строго от нижележащего через абстракции (интерфейсы), что гарантирует тестируемость (`@MockBean`) и слабую связанность (Loose Coupling).

### 1.3. Принципы SOLID в контексте проекта

* **S (Single Responsibility Principle — Принцип единственной ответственности):**  
  Каждый класс отвечает за одну задачу. `JwtTokenProvider` занимается только криптографической генерацией и парсингом токенов; `LoginAttemptService` — только счетчиком неудачных входов; `CsvService` — только сериализацией/десериализацией CSV.
* **O (Open/Closed Principle — Принцип открытости/закрытости):**  
  Фильтрация запросов через `DocumentRequestSpecification` открыта для добавления новых условий (новые предикаты) без изменения исходного кода репозитория.
* **L (Liskov Substitution Principle — Принцип подстановки Барбары Лисков):**  
  Реализация `UserPrincipal`, имплементирующая интерфейс `UserDetails`, может подставляться в любой механизм Spring Security без нарушения контракта авторизации.
* **I (Interface Segregation Principle — Принцип разделения интерфейсов):**  
  Вместо одного гигантского DAO-интерфейса объявлены точечные репозитории `AccountRepository`, `DocumentRequestRepository`, расширяющие специализированные интерфейсы `JpaRepository` и `JpaSpecificationExecutor`.
* **D (Dependency Inversion Principle — Принцип инверсии зависимостей):**  
  Сервисы зависят от абстракций интерфейсов репозиториев, а не от конкретных реализаций Hibernate. Внедрение зависимостей осуществляется через **Constructor Injection**.

## 3. Разбор серверной части (Backend) по слоям и пакетам

### 3.1. Инфраструктура, сборка и конфигурация

#### `backend/pom.xml`
* **Назначение:** Корневой дескриптор зависимостей и сборки проекта Maven.
* **Ключевые зависимости:**
  - `spring-boot-starter-web`: embedded Tomcat 10, Spring MVC, Jackson JSON.
  - `spring-boot-starter-security`: Spring Security 6, цепочка фильтров `SecurityFilterChain`, криптография BCrypt.
  - `spring-boot-starter-data-jpa`: Hibernate 6.4, Spring Data, HikariCP.
  - `spring-boot-starter-validation`: валидатор Hibernate Validator, спецификация JSR-380 (`@NotNull`, `@NotBlank`, `@Size`, `@Min`).
  - `postgresql`: JDBC-драйвер PostgreSQL.
  - `flyway-core`: система версионирования и автоматической миграции БД.
  - `spring-boot-starter-actuator`: эндпоинты мониторинга работоспособности сервиса (`/actuator/health`).
  - `springdoc-openapi-starter-webmvc-ui`: автогенерация документации OpenAPI 3.0 и интерактивного UI Swagger.
  - `jjwt-api`, `jjwt-impl`, `jjwt-jackson` (0.12.5): библиотека для генерации, подписи (HMAC-SHA512) и валидации JWT токенов.
  - `commons-csv`: потоковый парсер и генератор CSV файлов стандарта RFC 4180.

#### `backend/Dockerfile`
* **Назначение:** Сборка легковесного контейнера приложения.
* **Особенности:**
  - Базовый образ `eclipse-temurin:21-jre-alpine` (минималистичный дистрибутив Alpine Linux, размер ~180 МБ).
  - Установка утилиты `curl` (`apk add --no-cache curl`) для выполнения надежного healthcheck-запроса внутри контейнера.
  - Принцип **Build-Once-Run-Anywhere**: JAR-файл собирается Maven и копируется в контейнер.

#### `docker-compose.yml`
* **Назначение:** Декларативное развертывание двух связанных сервисов: `postgres` и `backend`.
* **Требование безопасности КР-3:** Публикация портов **только на localhost**:
  ```yaml
  ports:
    - "127.0.0.1:5432:5432" # postgres
    - "127.0.0.1:8080:8080" # backend
  ```
  Это исключает доступ к портам базы данных и сервиса из внешней локальной сети хост-машины.
* **Healthcheck & Depends-On:** Бэкенд не запустится до тех пор, пока контейнер PostgreSQL не рапортует `healthy` (через утилиту `pg_isready`).

#### `backend/src/main/resources/application.properties`
* `spring.jpa.hibernate.ddl-auto=validate`: жесткое требование промышленной разработки. Hibernate **не имеет права** модифицировать схему БД при запуске (`none/validate`). Он лишь проверяет строгое соответствие Java-сущностей реальным таблицам. Любые изменения схемы выполняются исключительно миграциями Flyway.
* `spring.jpa.open-in-view=false`: отключение опасного паттерна Open Session In View (OSIV), что предотвращает утечки соединений пула HikariCP во время рендеринга ответов.

### 3.2. Миграции базы данных Flyway (`db/migration`)

В КР-3 инициализация и обновление базы данных осуществляются версионируемыми миграциями Flyway:
* **`V1__init_schema.sql`**:
  - Создание расширения `pgcrypto` для генерации UUID v4 (`gen_random_uuid()`).
  - Таблица `users`: справочник заявителей архива (`id BIGSERIAL`, `full_name`, `email`, `department`, `is_active`, таймстампы).
  - Таблица `document_requests`: основная сущность запросов на выдачу документов (`id BIGSERIAL`, `uuid UUID NOT NULL UNIQUE`, `request_number VARCHAR NOT NULL UNIQUE`, `user_id BIGINT REFERENCES users(id)`, `document_title`, `category`, `status`, `priority`, `page_count`, `is_confidential`, `estimated_days`, `is_archived`, `version BIGINT NOT NULL DEFAULT 0`).
  - Таблица `document_request_tags`: теги основной сущности (составной первичный ключ `PRIMARY KEY (request_uuid, tag)` с каскадным удалением `ON DELETE CASCADE`).
  - Таблица `document_notes`: история заметок с возможностью закрепления (`id UUID PRIMARY KEY`, `request_uuid`, `author_username`, `content`, `is_pinned`).
  - Таблица `app_accounts`: учетные записи сотрудников системы (`id BIGSERIAL`, `username`, `password_hash`, `role`, `is_active`, `must_change_password`, `failed_login_attempts`, `locked_until`).
  - Таблица `refresh_sessions`: серверные сессии refresh-токенов (`id UUID PRIMARY KEY`, `account_id`, `token_hash`, `expires_at`, `revoked`).
  - Таблица `audit_logs`: журнал аудита безопасности (`id BIGSERIAL`, `username`, `event`, `entity_type`, `entity_id`, `correlation_id`, `details`, `created_at`).
  - **B-Tree Индексы:** созданы для ускорения полнотекстового поиска, фильтрации и соединений (`idx_doc_req_uuid`, `idx_doc_req_status`, `idx_doc_req_priority`, `idx_doc_req_user_id`, `idx_refresh_acc`, `idx_audit_event`).
* **`V2__seed_data.sql`**:
  - Начальные данные справочника заявителей и запросов архива. Учетные записи администратора и персонала инициализируются безопасным программным способом при старте Spring через BCrypt.

### 3.3. Модель данных и JPA-сущности (`domain`)

1. **`DocumentRequest` (Основная сущность):**
   * Содержит обязательные атрибуты КР-3:
     - `uuid` (`java.util.UUID`): неизменяемый глобальный уникальный идентификатор для клиентских операций.
     - `requestNumber` (`String`): внешний регистрационный код запроса (`REQ-2026-0001`).
     - `user` (`@ManyToOne` `ArchiveUser`): строгая связь с элементом справочника заявителей.
     - `status` (`@Enumerated(EnumType.STRING)`): `NEW`, `IN_PROGRESS`, `APPROVED`, `REJECTED`, `COMPLETED`, `CANCELLED`.
     - `priority` (`@Enumerated(EnumType.STRING)`): `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.
     - `pageCount` (`int`): числовой показатель (объем документа в страницах, >= 1).
     - `confidential` (`boolean`): логический признак ограничения доступа.
     - `estimatedDays` (`int`): **вычисляемый бизнес-показатель** (расчетный срок выдачи).
     - `archived` (`boolean`): признак мягкого удаления (soft delete) в архив.
     - `version` (`@Version Long`): поле версионирования для реализации оптимистической блокировки.
     - `tags` (`@ElementCollection`): коллекция строковых тегов.
     - `notes` (`@OneToMany`): список связанных заметок.
2. **`ArchiveUser` (Справочник):**
   * Представляет заявителя архивных материалов (сотрудники факультетов, студенты, внешние исследователи). Поле `active` позволяет отключать заявителей без нарушения целостности внешних ключей в базе.
3. **`Account` (Пользователи системы):**
   * Учетная запись оператора системы. Хранит признак `mustChangePassword` (обязанность сменить пароль при первом входе), счетчик `failedLoginAttempts` и дату временной блокировки `lockedUntil`.
4. **`RefreshSession` (Сессии обновления):**
   * Связывает аккаунт с уникальным хэшем refresh-токена, хранит дату истечения `expiresAt`, признак отзыва `revoked`, а также метаданные клиента (`userAgent`, `ipAddress`).
5. **`DocumentNote` (Заметки):**
   * Заметка с признаком `pinned` (закрепленная заметка отображается в начале списка).
6. **`AuditLog` (Журнал аудита):**
   * Запись о значимом действии с фиксацией логина, типа события, идентификатора сущности и `correlationId`.

### 3.4. Доступ к данным и динамические спецификации (`repository`)

#### `DocumentRequestSpecification.java`
* Реализует паттерн **Criteria Object / Specification** (интерфейс `org.springframework.data.jpa.domain.Specification`).
* Позволяет динамически собирать SQL-запрос `WHERE ... AND ...` в зависимости от переданных пользователем параметров:
  - Полнотекстовый поиск по подстроке (`documentTitle`, `requestNumber`, `category`, `description`).
  - Фильтрация по справочнику заявителей (`user.id`).
  - Фильтры по перечислениям (`status`, `priority`).
  - Фильтр по булевым флагам (`confidential`, `archived`).
  - Поиск по наличию конкретного тега (`join(DocumentRequest_.tags)`).
  - Числовые операции сравнения по количеству страниц (`eq`, `ne`, `gt`, `gte`, `lt`, `lte`).
* **Безопасность:** Использование Criteria API исключает риск **SQL Injection**, так как все параметры передаются через типизированные плейсхолдеры JDBC PreparedStatement.

## 5. Ключевые теоретические вопросы и инженерные механизмы КР-3

### 5.1. Гибридная аутентификация: Stateless JWT + Stateful Refresh Sessions
* **Проблема чистого JWT (Stateless):** JWT токен невозможно мгновенно отозвать до истечения его `exp` без введения тяжелых распределенных черных списков (Blacklist). Если токен скомпрометирован, злоумышленник имеет доступ до конца срока жизни.
* **Проблема чистого Session ID (Stateful):** требует обращения к базе данных при каждом HTTP-запросе, снижая горизонтальную масштабируемость системы.
* **Решение КР-3 — Гибридная схема:**
  1. **Access Token (JWT):** короткоживущий (15 минут). Не требует запросов к БД при проверке подписи на сервере.
  2. **Refresh Token (Opaque/UUID):** долгоживущий (7 дней). Привязан к серверной сессии в таблице `refresh_sessions`. При logout сессия мгновенно помечается `revoked = true` в БД, и злоумышленник больше не сможет обновить токен.

---

### 5.2. Криптография паролей: почему BCrypt, а не SHA-256?
В КР-2 использовался алгоритм SHA-256. В КР-3 осуществлен обязательный переход на **BCrypt**.
* **Уязвимость SHA-256:** SHA-256 проектировался как быстрый алгоритм вычисления контрольных сумм. Современные видеокарты (GPU) перебирают миллиарды хэшей SHA-256 в секунду, делая словарные атаки и атаки по радужным таблицам (Rainbow Tables) тривиальными.
* **Преимущества BCrypt:**
  1. **Криптографическая соль (Salt):** BCrypt автоматически генерирует уникальную 128-битную соль для каждого пароля и внедряет ее в результирующую строку `$2a$10$...`. Два одинаковых пароля получают абсолютно разные хэши, что делает радужные таблицы бесполезными.
  2. **Адаптивная вычислительная сложность (Work Factor / Cost):** параметр сложности (в проекте `strength = 10`) задает количество итераций ключевого расписания ($2^{10} = 1024$ раунда). Это намеренно замедляет вычисление одного хэша до ~50-100 мс на CPU, что делает полный перебор экономически и технически невозможным, не создавая заметной нагрузки для легитимных пользователей.

---

### 5.3. Защита от подбора паролей (Brute-Force Lockout)
* Сервис `LoginAttemptService` фиксирует неудачные попытки авторизации в разрезе логина пользователя.
* При 5 подряд неудачных попытках аккаунт блокируется на 15 минут (`locked_until = now() + 15 min`).
* Любая попытка входа в заблокированный аккаунт отклоняется исключением `LockedException` до проверки пароля, защищая хэш от атак по времени (Timing Attacks).
* При успешном входе счетчик неудач сбрасывается в 0.

---

### 5.4. Оптимистическая блокировка (`@Version`) и решение проблемы Lost Update
* **Проблема утерянного обновления (Lost Update):**
  Оператор А и оператор Б одновременно открывают документ версии 0. Оператор А меняет статус на `IN_PROGRESS` и сохраняет (версия становится 1). Оператор Б, не видя правок оператора А, меняет название и сохраняет. Без контроля блокировок изменения оператора А будут перезаписаны и утеряны.
* **Реализация в КР-3:**
  В сущности `DocumentRequest` объявлено поле `@Version private Long version;`.
  При сохранении Hibernate генерирует запрос:
  ```sql
  UPDATE document_requests 
  SET document_title = ?, status = ?, version = 1 
  WHERE id = ? AND version = 0;
  ```
  Если версия в базе уже изменилась, запрос обновляет 0 строк. Hibernate выбрасывает `OptimisticLockException`, сервис переводит его в `VersionConflictException`, а клиент получает HTTP-код `409 Conflict` с понятным уведомлением о необходимости обновить данные.

---

### 5.5. Вычисляемый показатель `estimatedDays` (Бизнес-метрика)
В соответствии с требованиями КР-3, основная сущность включает вычисляемый показатель — **расчетный срок исполнения архивного запроса в рабочих днях**.

**Алгоритм расчета (`DocumentRequestService.calculateEstimatedDays`):**
$$\text{estimatedDays} = \text{baseDays}(\text{pageCount}) + \text{priorityModifier} + \text{confidentialModifier}$$
1. **Базовый срок по объему документов (`pageCount`):**
   * до 20 страниц: $3$ дня;
   * от 21 до 50 страниц: $4$ дня;
   * от 51 до 100 страниц: $5$ дней;
   * свыше 100 страниц: $6$ дней.
2. **Модификатор приоритета:**
   * `CRITICAL`: $-2$ дня (ускоренная обработка, минимум 1 день);
   * `HIGH`: $-1$ день;
   * `MEDIUM`: $0$ дней;
   * `LOW`: $+1$ день.
3. **Модификатор секретности:**
   * `confidential = true`: $+1$ день (требуется дополнительное согласование службы безопасности фонда).

Показатель автоматически пересчитывается при создании или обновлении параметров документа.

---

### 5.6. Двухэтапный импорт CSV (Preview Validation → Batch Apply)
Для предотвращения загрязнения базы данных некорректными записями процедура импорта разделена на два изолированных шага:
1. **Этап 1: Предпросмотр (`POST /api/document-requests/import/preview`):**
   - Парсинг CSV с помощью Apache Commons CSV.
   - Построчная валидация типов, обязательности полей и существования заявителей в справочнике.
   - Возврат клиенту статистики: `totalRows`, `validRows`, `invalidRows` и разобранных данных без записи в БД.
2. **Этап 2: Применение (`POST /api/document-requests/import/apply`):**
   - Выполняется только после подтверждения пользователем.
   - Поддерживает два режима:
     * `CREATE_ONLY`: импортируются только новые записи, совпадающие коды пропускаются.
     * `UPDATE_EXISTING`: новые создаются, а существующие обновляются по внешнему коду `request_number`.

---

### 5.7. Сквозная трассировка запросов через Correlation ID и MDC
* При поступлении HTTP-запроса фильтр `CorrelationIdFilter` извлекает или генерирует уникальный идентификатор:
  `X-Correlation-ID: e62a98f7-7bf0-4b21-995a-2cb79a3fa270`.
* Идентификатор помещается в **MDC (Mapped Diagnostic Context)** потока обработки запроса библиотеки SLF4J/Logback.
* Каждая строчка лога в консоли бэкенда автоматически маркируется данным ID.
* Тот же Correlation ID сохраняется в журнал аудита `audit_logs.correlation_id` и возвращается в теле любой ошибки клиенту, что позволяет администратору за секунду найти точную причину сбоя в логах сервера.

---

### 5.8. Hibernate `ddl-auto: validate` и миграции Flyway
* Использование `ddl-auto: update` или `create` в продакшене категорически запрещено: Hibernate может случайно удалить колонки с данными при переименовании полей или сгенерировать неоптимальные типы.
* В КР-3 управление DDL передано миграциям Flyway, а Hibernate работает в режиме `validate`. При старте приложения Hibernate лишь проверяет метаданные: если в БД тип колонки `INTEGER`, а в JPA сущности объявлен `Long` (`BIGINT`), запуск приложения аварийно прерывается с ясным сообщением об ошибке несовместимости схемы, исключая порчу данных во время работы.

---

### 5.9. Сетевая безопасность Docker: привязка к `127.0.0.1`
* По умолчанию Docker публикует порты на интерфейсе `0.0.0.0` (Insecure), что открывает доступ к БД и API любому устройству в локальной сети Wi-Fi или Ethernet.
* В файле `docker-compose.yml` порты явно забинжены на loopback-интерфейс `127.0.0.1:8080:8080` и `127.0.0.1:5432:5432`, что полностью изолирует сервисы от внешнего сетевого периметра хост-машины.
